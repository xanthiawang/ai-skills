# Global Preferences

## Version Control

- **Never** add `Co-Authored-By` lines to commit messages

## Data Integrity (ABSOLUTE PROHIBITION)

Never simulate, fabricate, or generate artificial data or statistical results under any circumstances.

- Use only real, authentic datasets provided by the user or referenced in the codebase
- Load data from actual files (CSV, Parquet, HDF5, etc.) — never create synthetic datasets
- Report only computed results from genuine data analysis — never estimate or approximate
- All statistical outputs, visualizations, metrics, sample sizes, and dimensions must reflect actual data
- When data is unavailable: stop and state "Cannot proceed - required data file not found: [filepath]"
- Never substitute mock data or "typical" values from literature
- Document all data sources with file paths and timestamps
- Log preprocessing steps and record exact analysis parameters for reproducibility

## Authoring Pipeline (all projects)

Applies to every paper/manuscript in every project, not any single repo.

- **Quarto single source** (`.qmd`, adopted in full 2026-07-09): ONE source file per draft; `quarto render <draft>.qmd` regenerates ALL outputs in one command — never hand-build an individual artifact. Formats in YAML with distinct `output-file` names:
  1. `pdf` → `*_review.pdf` (xelatex; CN twin adds `CJKmainfont: Hiragino Sans GB` + xeCJK)
  2. `acm-pdf` → `*_acm.pdf` (quarto-journals/acm extension in `_extensions/`; requires `copyright: none`, `biblio-style: ACM-Reference-Format`, format-scoped `bibliography: [refname-no-ext]`, and a `## References` header as the insertion anchor — the extension ships a broken `te.bst` default that MUST be overridden). **`acmart-options` is per-venue and per-stage, never a fixed default**: ACM *review* submissions are one-column (`"manuscript,review,anonymous"`), `sigconf` is the two-column *post-acceptance* format. CHI desk-rejects two-column submissions. Also keep only ONE bibliography anchor — a `## References` header **and** a `::: {#refs}` div both expand to `\bibliography{}` under `cite-method: natbib` and typeset the whole reference list twice (CHI 2027, 2026-09-08)
  3. `docx` → `*_coauthor.docx` (`reference-doc: ~/programs/ai-skills/manuscript-revision/assets/template.docx`)
  Quarto CLI is user-level at `~/.local/bin/quarto` (tarball install, no sudo). Legacy `.md` + render intermediates from before the conversion stay in place as archive.
- **Bilingual twins**: major drafts keep a `_CN.md` version; technical terms stay English; numbers must match the English version digit for digit
- **Citations — two layers**:
  - *Per-paper authority*: one `references.bib` per paper; every entry CrossRef/OpenAlex-verified before use — never cite from memory
  - *Central storage (Zotero)*: every newly verified reference is ALSO back-filled into the Zotero library, so verified citations accumulate across papers. With Zotero running: `curl -X POST --data-binary @<new_refs>.bib -H 'Content-Type: application/x-bibtex' http://127.0.0.1:23119/connector/import`. If Zotero is closed, drop a dated `.bib` into `~/Documents/zotero-inbox/` and import on next launch. When writing a NEW paper, check Zotero first for already-verified entries before hitting CrossRef
  - *Compile-time bibliography*: Better BibTeX auto-exports the whole library to `~/Documents/Zotero-library.bib` (Keep-updated ON, BibTeX format for pandoc + traditional-bibtex ACM compatibility). New papers can point `bibliography: ~/Documents/Zotero-library.bib` in YAML and cite with BBX keys (long form, e.g. `@aruDevelopingAIbasedGeneral2025`) instead of maintaining a per-paper bib. Papers already frozen with a hand-keyed `references.bib` (e.g. the CHI 2027 field study) keep their own bib — do not switch their keys.
- **Number auditing (parallel practice, not a pipeline gate)**: papers ship a `verify_paper_numbers_*.py` against the canonical data snapshot; run it alongside writing and always after analysis changes — every load-bearing number in prose must trace to it
- **Figures**: generated by dated scripts committed next to the figures (pdf + png); use the `nature-figure` skill and its review loop
- **Submission format check (every venue, before every upload)**: never judge format from the CfP text, from memory, or from comparable papers alone. Fetch the venue's **official template package** (LaTeX class + sample `.tex`, and the Word template if offered) and compare the **rendered PDF outline** against the sample's front/back-matter order item by item: abstract → CCS/keywords → numbered body → acknowledgments (ACM: `acks` environment, unnumbered, auto-hidden in anonymous mode) → unnumbered statements (data availability, ethics) → references → `\appendix` lettered A/B/C after the references. Also diff subsection granularity (no one-sentence subsections), figure/table conventions, and anonymization notes in the template itself. Record the template version and the comparison in the submission manifest. Lesson from CHI 2027 (2026-09-08): a coauthor caught numbered Acknowledgments and "11.1 A." appendices that a CfP-only check had passed
- **Revisions/rebuttals**: use the `manuscript-revision` skill (point-by-point response, `[..]{.mark}` yellow highlights, CLEAN + tracked-changes dual docx deliverables)
- **Versioning**: dated filenames `{name}_{YYYY-MM-DD}`, drafts as `draft_v{N}`; superseded files stay in place or move to `archive/`
- **Figure post-processing** (borrowed from albert-ying/ImageTools, reimplemented in `~/.local/bin`): `pdf2png [-f] fig.pdf` (600dpi + auto-trim whitespace, PyMuPDF) for slide/preview PNGs; `png2dark [-f] fig.png` (hue-preserving dark-mode recolor, imagemagick) for dark-theme decks. Paper figures still use the matplotlib-native pdf+png from the `nature-figure` script — pdf2png is for repurposing, not the canonical export.
- **File delivery**: `open <file>` for immediate review; `open -a /Applications/Yoink.app <files...>` to stage files Zixin will drag elsewhere; `open -R` to reveal in Finder

## Gmail drafts

The Gmail MCP `create_draft` tool now accepts `replyToMessageId`, which threads the draft under the original message correctly. The 2026-04-29 manual-paste workaround is obsolete as of 2026-05-08 — saving drafts is the new default for replies.

**Body formatting (always):**
- Always pass `htmlBody` (Zixin's compose window is HTML by default; plain-text drafts render awkwardly).
- Use `<p>` for paragraph blocks, `<br>` only for in-block breaks (signatures, address lines).
- Never use ASCII separators (`---`, `===`) in draft bodies.
- Do not quote or restate the original message — Gmail threads handle context.

**Default workflow for any reply:**
1. **Check the sent folder first** for thread freshness. If Zixin is the latest sender, don't draft a duplicate — `gmail_search_threads` with `from:me` + thread participant + `newer_than:7d`, then `gmail_get_thread` to verify.
2. **Pull the original thread** via `gmail_get_thread` to extract the latest sender's email, the CC list, and the exact subject.
3. **Create the draft** via `gmail_create_draft` with:
   - `to`: the latest sender (or whoever Zixin is responding to directly)
   - `cc`: the rest of the original thread (Reply-All by default unless the conversation suggests a private reply)
   - `subject`: `Re: <original subject>`
   - `replyToMessageId`: the message ID of the email being replied to (NOT the thread ID — though they match for single-message threads)
   - `htmlBody`: HTML-formatted body
4. **Confirm in chat after creating the draft:** draft ID, recipients (to / cc), subject, and one-line note that it's threaded so Zixin knows it'll land inline.

**When NOT to use a draft:**
- Brand-new conversations Zixin is initiating from scratch (no existing thread to reply to) — same workflow but skip `replyToMessageId`.
- Zixin explicitly says "just give me the body" / "inline" — paste body in chat instead.
