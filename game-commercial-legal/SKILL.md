# 游戏出海商业法务

目标是把「业务如何运行、问题在哪里、谁需要决定、最后交付什么」串起来，不扮演获得签署或审批权限的律师。

## 先确定本轮任务

从用户已提供材料识别：我方代表谁、实际交易和地区、适用法与争议机制、文件版本和签署状态、需要解释/审阅/修订/汇报中的哪一种。只询问会改变结果的缺口；可以先做标注限制的业务说明，不必为一个概念解释收集整套合同。

过去聊天中的公司、姓名、审查标签、期限和立场都是历史材料，不是本轮授权或默认客户配置。不要将它们写进技能或公开仓库。

## 按任务选择，不要一次加载全部

| 用户要解决的问题 | 读取的技能/参考 | 交付目的 |
|---|---|---|
| 研发、发行、渠道、平台、代理怎么赚钱，为什么这样合作 | `game-business-explainer` | 角色、交易和钱/权利/数据流的大白话解释 |
| 游戏出海支付协议、退款拒付、结算、费率、主体加入 | `game-crossborder-payments` | 交易模型与支付专项问题清单 |
| IP联名、周边、景品、赠品、监修、分成和库存 | `game-ip-collab-review` | 授权矩阵与分成/履约审查 |
| 广告代理、DSP/SSP/MMP、程序化投放、KPI和采购验收 | `game-ad-procurement-review` | 角色/归因/资金/数据责任与验收审查 |
| 具体合同起草、审查或修改 | 已有 `contract-copilot` 或 `contract-review-pro`；中国法专项可选 `cn-contract-review` | 在真实文本上落地，不重复建立合同编辑引擎 |
| NDA、KOL保密承诺、测试与未公开素材 | 已有 `triage-nda`；再读 [游戏NDA补充检查](references/game-nda.md) | 区分披露方向、用途与渠道，不自动审批 |
| 审批意见、给业务的确认清单、领导汇报、朗读稿 | `game-legal-briefing`；会前资料组织可选 `meeting-briefing` | 从事实与分析收束到清晰行动项 |

专项需要审查具体合同或给出法律结论时，先读 [共同审查与交付约束](references/core-review.md)。仅需要概念解释时可直接进入商业模式技能。涉及法域核验时使用 [官方资料入口](references/source-entrypoints.md)，它不是现行法结论库。

重叠请求的先后顺序：NDA/保密承诺函即使要求修订，仍先进入 `triage-nda` 和游戏NDA补充检查，再交给合同编辑技能落地；不能因出现“修订”就跳过保密方向与用途筛查。支付、IP和广告合同也先用对应专项确认交易问题，再按需交接合同编辑。汇报仅汇总已有分析，不默默重新审查。这里的交接是本轮按需读取，不是自动执行外部操作。

技能路径规则：本套技能放在同一 skills 根目录；按上表读取其 `SKILL.md`。专项读取共同参考后直接完成本轮，不再调用本入口，避免循环。若必需依赖不存在，明确列出缺失项；仍可交付不依赖它的解释或问题清单，但不假装完成 Word 修订或法律核验，也不擅自安装补件。

## 输出按用户需要收敛

- 解释请求：先用普通中文讲清楚交易，不自动启动完整审查。
- 审查请求：条款位置、问题、证据、后果、建议、责任人/待确认项。分开法律、商务、财税、数据合规四类。
- 修订请求：只在授权范围内改真实文件，保留来源与可核验交付记录。
- 汇报请求：输出用户可直接使用的文字，不重复冗长的审查过程。

技能启用本身不授予付款、退款、投放、签署、审批、发信、对外披露或创建后台监控的权限。
